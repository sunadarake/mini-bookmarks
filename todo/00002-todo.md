# publish.sh を公開リリース作成と旧リリース削除に変更

## 概要
`publish.sh` は現在、GitHub にドラフトのリリースを作成して手動公開を促している。
これを、ビルド後にそのまま公開リリースを作成し、成功したら以前のリリースとタグを削除する挙動に変える。

## 調査結果
- `publish.sh` は `gh release create ... --draft --target HEAD` でドラフトを作成し、最後に手動公開を促している
- タグはドラフト作成時ではなく公開時に作られる（スクリプトのコメントにも記載）
- 削除対象の特定には `gh release list`（既定は作成日の降順）を使える
- `gh release delete --cleanup-tag` はリリースとタグをまとめて削除できるが、タグが無いドラフトでは失敗する可能性がある
- 既存のリリースは `v3.0.0` の1件のみ

## 実装計画
- [x] ステップ1: `publish.sh` のヘッダーコメントを「公開リリースを作成し、以前のリリースとタグを削除する」に更新する
- [x] ステップ2: `publish.sh` で、新リリース作成前に「新タグ以外の最新リリース1件」と「新タグ以外のドラフトリリース」を `gh release list --json` で取得しておく
- [x] ステップ3: `publish.sh` の `gh release create` から `--draft` を外し、公開リリースを作成する
- [x] ステップ4: 新リリース作成成功後に、事前に取得した旧リリースを削除する。リモートにタグがあれば `--cleanup-tag` 付き、無ければリリースのみ削除する
- [x] ステップ5: `publish.sh` 末尾のメッセージを「公開しました」「旧リリースを削除しました」に更新する
- [x] ステップ6: `AGENTS.md` の `publish.sh` の説明を、公開リリース作成と旧リリース・タグ削除に更新する

## テスト・確認方法
- [x] `bash -n publish.sh` で構文チェックが通る
- [x] `shellcheck publish.sh` で警告が出ない（既存由来の指摘を除く）
- [x] `gh release list` の `--jq` 式を実データで実行し、削除対象が正しく1件（`v3.0.0`）になることを確認する
- [x] `git diff` で変更内容を確認する（実際のリリース作成・削除は実行しない）

## 決定事項
- 公開リリースとして作成する（ドラフトにしない）
- 削除対象は「新タグ以外の最新リリース1件」に加え、新タグ以外のドラフトリリース
- 削除は新リリース作成が成功した後に行う
- 旧リリースの特定は新リリース作成前に済ませておく

## 懸念点・未決事項
- 最新リリースがドラフトだった場合、公開済みの旧リリースは残る（「最新1件」の指定どおり）
- `build.sh` の案内文には「提出後に git tag を付ける」とあり、`publish.sh` がタグを作る新挙動と重複する。今回は範囲外として変更しない
- `gh release delete --cleanup-tag` をタグ無しのドラフトに使うと失敗しうるため、リモートタグの有無を `git ls-remote` で確認して分岐する
