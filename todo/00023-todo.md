# build/release スクリプトを整備する

## 概要
配布用 zip の作成先を `build/` に変更し、GitHub リリース用の `release.sh` を新設する。`generate_key.sh` は既存の `key` を削除してから拡張 ID を入れ直す動きにする。既存の `publish.sh` は `release.sh` に置き換えて削除する。

## 調査結果
- `build.sh` はテスト実行後、`dist/mini-bookmarks-v{version}.zip` を作り、旧 zip を削除している
- `publish.sh` は `build.sh` を呼び、`dist/` の zip を GitHub に公開リリースし、直前のリリースとドラフトを削除している
- `generate_key.sh` は `manifest.json` に `key` があると何もせず終了する。`key.pem` はルートにあり、`.gitignore` の `*.pem` で無視されている
- `manifest.json` の `version` がバージョンの唯一の定義元。`package.json` の `name` は `mini-bookmarks`
- `.gitignore` には `/build`、`/dist`、`key.pem`、`*.pem` がある
- `AGENTS.md` と `README.md` に `build.sh` の出力先 `dist/` と `publish.sh` の記述がある

## 実装計画
- [x] ステップ1: `build.sh` を変更し、テストを実行せず `build/{extension name}-v{version}.zip` を作る。作成前に `build/` 内の旧バージョン zip を削除し、経過と結果を相対パスで表示する
- [x] ステップ2: `release.sh` を新規作成する。`mktemp -d` の一時ディレクトリに zip を作り、概要とインストール方法を書いたリリースノートで GitHub に公開リリースする。終了時に一時ディレクトリを削除し、作成成功後に新バージョン以外のすべてのリリースとタグを削除する
- [x] ステップ3: `generate_key.sh` を変更し、`manifest.json` に既存の `key` があれば削除してから、既存の `key.pem`（無ければ新規作成）で拡張 ID を入れ直す
- [x] ステップ4: `publish.sh` を削除する
- [x] ステップ5: `AGENTS.md` と `README.md` のビルド出力先・リリースコマンドの記述を新しいスクリプトに合わせる

## テスト・確認方法
- [x] `bash -n build.sh release.sh generate_key.sh` で構文を確認する
- [x] `./build.sh` を実行し、`build/mini-bookmarks-v{version}.zip` が作成され、旧バージョンの zip が削除されることを確認する
- [x] `generate_key.sh` を一時ディレクトリに複製した `manifest.json` / `key.pem` で実行し、既存 `key` が削除されたうえで再設定されることを確認する
- [x] `./release.sh` は実際のリリースが発生するため実行せず、`bash -n` と内容の確認にとどめる
- [x] `pnpm test` と `pnpm run lint` が通る

## 決定事項
- `build.sh` ではテストを実行しない
- `release.sh` は `build.sh` を呼ばず、一時ディレクトリに直接 zip を作る
- 以前のリリースは新バージョン以外のすべてを削除する
- `generate_key.sh` は既存の `key.pem` を再利用する
- `publish.sh` は削除して `release.sh` に一本化する

## 懸念点・未決事項
